# Rogue AutoBattler — Архитектурный дизайн-док

> **Жанр:** Roguelike RPG AutoBattler
> **Стек:** Godot 4.3+, GDScript (статически типизированный)
> **Целевой объём:** Полугодовой проект
> **Версия документа:** 1.0

---

## 1. Концепция и фикс-фреймворк

Игрок собирает отряд из нанятых юнитов на сетке `N × N`, расставляет перед раундом. Бой идёт автоматически (тиковая симуляция, не реальное время): цель — выжить серию раундов против процедурных врагов, между раундами — магазин, прокачка, выбор наград.

**Ключевые ссылки по жанру:** TFT, Dota Auto Chess, Storybook Brawl, Backpack Battles.

**Принципы разработки:**

1. **Данные отделены от логики.** Контент — это `.tres` ресурсы. Логика — это переиспользуемые скрипты.
2. **Логика отделена от визуала.** `core/` ничего не знает о нодах. `scenes/` и `content/` не знают о правилах.
3. **Детерминизм.** Любой раунд воспроизводим по seed.
4. **Расширяемость через композицию.** Новый юнит/эффект/способность = новый ресурс, без правки ядра.
5. **Сохранение с миграциями.** Версия сейва — это контракт.

## 3. Игровой цикл (Run Loop)

```
┌─────────────┐
│  Main Menu  │
└──────┬──────┘
       │ Start Run
       ▼
┌─────────────┐         ┌──────────────┐
│ Shop / Prep │────────►│  Battle Run  │
│  (покупка,  │ ◄───────│  (тиковый    │
│  расстановка)│   next │   бой)       │
└──────┬──────┘  round └──────┬───────┘
       │                       │
       │ Death                 │ Win
       ▼                       ▼
┌─────────────┐         ┌──────────────┐
│ Game Over   │         │ Award Screen │
└─────────────┘         └──────────────┘
```

**Состояние рана** (`RunState`):
- `seed: int` — детерминизм.
- `round: int`.
- `gold: int`, `xp: int`, `level: int`.
- `board: Array[Combatant]`.
- `bench: Array[Combatant]`.
- `enemy_wave: Array[Combatant]`.
- `meta_modifiers: Dictionary` — баффы между раундами.

## 4. Сетка и позиционирование

- Сетка: `Grid` — двумерный массив `Vector2i`.
- Стороны: `Team.PLAYER`, `Team.ENEMY`. Каждый юнит привязан к стороне + ячейке.
- Размер сетки настраивается (`Vector2i Grid.SIZE = Vector2i(7, 4)` — длина × ширина).
- Занятость проверяется через `Grid.is_occupied(cell)`.
- **Нет** физики — все позиции вычисляются аналитически по координатам.

**Правила движения (расширяемые):**
- По умолчанию: юнит атакует/двигается только к врагам в пределах своей стороны + 1 ряд.
- При первом проходе архитектура поддерживает только стандартную сетку. «Линии и колонки» (как в TFT) — будущее расширение через `LineRule`/`ColumnRule`.

## 5. Бой и временная модель

**Tick-based симуляция**, не реальное время:

```
battle_time = 0.0   # секунды с начала боя
tick_dt = 0.05      # шаг симуляции (20 тиков/сек)
```

На каждом тике `BattleRunner.step(dt)`:
1. Для каждого живого юнита:
   - Пересчитать кулдауны способностей и эффектов.
   - AI выбирает действие (цель для атаки / способности).
   - Применить действие.
2. Обновить DOT-эффекты.
3. Удалить мёртвых.
4. Если одна из сторон пуста — бой окончен.

**Детерминизм:**
- Все случайные решения прокинуты через `RngService`, привязанный к `run_seed + battle_seed`.
- Никаких `randf()` напрямую в логике — только через сервис.

**AI:** базовая стратегия — «ближайший враг по прямой», заменяема через интерфейс `AiController`.

## 6. Эффекты — система, открытая к расширению

**`Effect`** — это переиспользуемый кусок логики, который принимает `BattleContext` и `EffectInstance`. Применяется к одной или нескольким целям.

Базовые эффекты v1:
- `DamageEffect` — наносит урон (физ/маг) с учётом броне/сопротивлений.
- `HealEffect` — восстанавливает HP.
- `ApplyStatusEffect` — накладывает статус (`StatusDef`).
- `MoveEffect` — перемещает на N клеток.
- `SummonEffect` — спавнит юнита.

**Расширение:** добавить новый эффект = создать новый скрипт-наследник `Effect` и `.tres` с параметрами. Без правки ядра.

**Статусы** (тонкие модификаторы состояния): `BURN`, `STUN`, `ATK_UP`, `SHIELD`, `REGEN`, `POISON`. Каждый — ресурс `StatusDef` с длительностью, тиками, модификаторами.

## 7. Способности

**`AbilityDef`** (Resource): id, имя, иконка, описание, кулдаун, mana_cost, targeting, `effects: Array[Effect]`.

**Targeting:**
- `SINGLE_ENEMY`
- `SINGLE_ALLY`
- `AOE_CIRCLE`
- `AOE_LINE`
- `AOE_CONE`
- `SELF`
- `RANDOM_ENEMY`

**Применение:** `AbilityResolver.resolve(ability, caster, target) → Array[EffectApplication]`.

**Композиция:** способность — это просто набор эффектов с условием срабатывания. Хочешь «огненный шар, который наносит урон и поджигает» = `[DamageEffect, ApplyStatusEffect(BURN)]`.

## 8. Ресурсы данных (`.tres`)

Все игровые сущности — это `Resource`-классы с `@export` полями:

```gdscript
# core/data/unit_def.gd
class_name UnitDef extends Resource
@export var id: StringName
@export var display_name: String
@export var icon: Texture2D
@export var max_hp: int
@export var attack: int
@export var defense: int
@export var attack_speed: float  # атак в секунду
@export var move_speed: float    # клеток в секунду
@export var attack_range: int    # в клетках
@export var team: Team
@export var tier: int            # 1..5 для цены
@export var cost: int
@export var abilities: Array[AbilityDef]
@export_multiline var description: String
```

Аналогично: `AbilityDef`, `StatusDef`, `ItemDef`, `EnemyWaveDef`.

**Хранение контента:** контент лежит в `content/**/*.tres` и загружается через `ContentDB` (синглтон-сервис), который:
- Сканирует папки при старте (через `ResourceLoader.list_directory`).
- Кэширует по id.
- Поддерживает хотрелоад в редакторе.

## 9. Экономика и мета

- **Золото** — покупки в магазине между раундами. Получается за раунды, серии побед, проигрыши (как в TFT).
- **Unit shop** (`RunController.shop`) — предложения юнитов для найма между боями.
- **Merchant shop** (`RunController.merchant_shop`) — отдельные предложения предметов для MERCHANT encounter; API двух магазинов не смешиваются.
- **XP / Level** — сколько юнитов можно ставить на доску.
- **Интерес-кривая** — стоимость юнитов, тиры, синергии (отложено в v2).
- **Мета-профиль:** постоянный `MetaProfile` с разблокировками, статистикой, настройками. Сохраняется отдельно от рана.

## 10. Сохранения и миграции

Файлы: `user://saves/meta.tres`, `user://saves/runs/<seed>.tres`.

Каждый сейв имеет поле `version: int`. `SaveManager` при загрузке прогоняет сейв через цепочку миграций `migrate_v1_to_v2 → v2_to_v3 → …`.

Текущая версия: **1**.

## 11. Autoload (глобальные сервисы)

| Имя        | Назначение                                        |
|------------|---------------------------------------------------|
| `Logger`   | Логирование с тегами и уровнями                  |
| `EventBus` | Глобальные сигналы (unit_died, round_started, …)  |
| `RngService` | Детерминированный RNG с seed                       |
| `ContentDB`  | Загрузка и кэширование контентных ресурсов      |
| `SaveManager`| Чтение/запись сейвов с миграциями                |

Все autoload — это `Node`-обёртки над чистыми классами (которые лежат в `core/utils/` и тестируются отдельно).

### UI lifecycle в Web build

- `RootScene` — полноэкранный `Control`, владеющий `MainMenu` и лениво создаваемым `BattleScene`.
- `MainMenu` только эмитит `run_requested(seed)`; scene-код не удаляет детей `/root`, поэтому autoload-узлы сохраняются весь runtime.
- При входе в `REWARD` `BattleScene` передаёт offer и `RunController` в `RewardModal` напрямую. `EventBus.reward_offered` остаётся дополнительным уведомлением, а не единственным источником UI-state.

## 12. Соглашения по коду

- GDScript v2, **статически типизированный** везде: `var hp: int`, `func _ready() -> void:`.
- Все классы с `class_name` объявляются в snake_case файлах.
- Все публичные методы — с документационными комментариями `##`.
- Никаких `print()` в проде — только `Logger`.
- Без `randf()` / `randi()` напрямую — только через `RngService`.
- Имена файлов = имя класса (например, `unit_def.gd` → `class_name UnitDef`).
- `core/` не импортирует ноды. Никаких `Node`, `Sprite2D` в `core/`.

---

## 13. Что НЕ делаем в v1

Чтобы не раздувать скоуп полугодового проекта, в первой версии **намеренно отсутствуют**:

- Синергии и классы юнитов (предлагаются в v2).
- Экипировка и предметы (отдельный модуль в v3).
- Мультиплеер и кооп.
- Реплеи.
- Туториал (отдельной сценой).
- Steam-интеграция.

Эти направления зарезервированы в архитектуре, но не реализованы.

## 16. Открытые вопросы (для уточнения)

Эти решения влияют на архитектуру и должны быть приняты до v0.4:

1. **Сетка.** Какой размер по умолчанию? 7×4 как TFT или меньше для мобил?
2. **Кооп/сингл.** Планируется ли PvP / кооп? (Влияет на серверную архитектуру.)
3. **3D vs 2D.** Предполагаю 2D для скорости разработки. Подтвердить.
4. **Стиль арта.** Pixel-art, hand-drawn, минимализм, 3D-превью? Влияет на пайплайн ассетов.
5. **Длительность рана.** 5 раундов (быстрый) или 20+ (длинный)?
6. **Темп.** Tick-based настраивается пользователем (ускорение ×1/×2/×4)?

По умолчанию при отсутствии ответа: 7×4, сингл, 2D, pixel-art (опционально), 10–12 раундов, с возможностью ускорения.
